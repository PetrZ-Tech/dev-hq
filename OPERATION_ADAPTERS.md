# Наблюдение результатов операций — версия 1.3

Архитектура сохраняется: пользователь → ChatGPT Plus / Chat → skill → плагин → проверка.
Локальные Python-команды сохраняют метаданные, запускают явно запрошенную команду или читают состояние. Они не обращаются к моделям, не создают агентов и не продолжают остановленный чат.

## Общие правила

Сначала зарегистрировать potentially long operation через task_lifecycle.py begin-operation. Ожидаемый срок относится к операции, а не ко всем задачам сразу. Сохранить operation.id. Без регистрации охвата нет. Для побочного эффекта нужен стабильный action-key; защита действует внутри run.

Наблюдение никогда не заменяет проверку результата. RESULT_AVAILABLE означает наличие подтверждения завершения конкретного вызова, затем ChatGPT проверяет exit code, артефакты и критерии задачи и записывает succeeded. Активная операция блокирует finish, даже если адаптер видит RESULT_AVAILABLE.

При FAILED, OUTCOME_UNKNOWN или OVERDUE сначала read-only диагностика. Повторять неизвестный побочный эффект вслепую нельзя. Монитор не делает retries, не убивает процессы и не возобновляет чат.

## Явно запущенный локальный процесс

После begin-operation с типом terminal/test/build:

~~~powershell
python -B scripts/observed_process.py --run <run-id> --operation <operation-id> --cwd <PROJECTS_ROOT>\<project> --timeout 300 -- python -B <test-script.py>
~~~

Использовать только для уже разрешённой явной команды. shell=False; stdout/stderr этой обёрткой не сохраняются. Если нужны результаты тестов, сама команда должна сохранить безопасный файл отчёта для проверки.

Обёртка связывает операцию с файлом результата до запуска и создаёт эксклюзивный claim. Затем сохраняет PID + время создания, exit code и время завершения. Второй запуск той же связанной операции блокируется. Claim не очищается автоматически при ошибке.

- Тот же PID/creation identity без результата: WAITING_RESULT в пределах срока, затем OVERDUE.
- Exit 0 с корректным файлом: RESULT_AVAILABLE.
- Ненулевой exit: FAILED.
- Timeout, исчезнувший процесс без подтверждения или повреждённые метаданные: OUTCOME_UNKNOWN.
- Timeout не завершает дочерний процесс. Проверить его фактический исход отдельно.

Команда не подтверждает смысловую корректность артефакта. Родительский run и незавершённые action keys сохранять при смене чата.

## n8n через существующий плагин

1. Зарегистрировать operation до вызова.
2. В ChatGPT вызвать n8n Connector get_workflow_execution с точными workflowId/executionId и includeData=false.
3. Сразу сохранить только разрешённые метаданные ответа в обычный JSON внутри Projects: объект execution с id, workflowId, status, startedAt, stoppedAt, waitTill.
4. Зарегистрировать свежий ответ:

~~~powershell
python -B scripts/task_lifecycle.py observe-n8n --run <run-id> --operation <operation-id> --workflow-id <workflow-id> --execution-id <execution-id> --response-file <PROJECTS_ROOT>\<project>\runtime\n8n-response.json --evidence-ref <tool-result-reference> --max-age 120
~~~

Сохранять ответ немедленно после нового вызова плагина. Нельзя повторно подавать старый JSON, выдавая его за новую проверку: эта кооперативная схема не удостоверяет источник ответа криптографически.

Наблюдатель читает локальный снимок, а не обращается к n8n напрямую. Обновить снимок может ChatGPT после нового read-only вызова плагина. Если чат остановился и снимок старше max-age, состояние UNKNOWN. Ни новых credentials, ни фонового API-клиента не добавлено.

Снимок ограничен 32 KB, TTL 10–600 секунд. Идентичности run, operation, workflow и execution должны совпасть. Обновление снимка не продлевает deadline и не меняет semantic progress.

| Статус n8n | Наблюдение |
|---|---|
| new / running / waiting | WAITING_RESULT, затем OVERDUE при превышении срока |
| success | RESULT_AVAILABLE до отдельной проверки/acknowledgement |
| error / crashed / canceled | FAILED |
| неизвестный, устаревший, некорректный | OUTCOME_UNKNOWN |

waiting n8n означает ожидание внешнего задания, а не автоматически ответ пользователя.
По умолчанию execution должен начаться после начала operation. Флаг --historical использовать исключительно для явно названного аудита старого execution; это не свидетельство нового запуска.

Production workflow для проверки этого адаптера не запускать и не менять. Реальный read-only тест старого execution и искусственные сценарии running/error/timeout различать в отчёте.

## Локальные уведомления

http://127.0.0.1:32110/hq-status показывает Attention и Next action; /api/status содержит notification. Приоритет: FAILED → OUTCOME_UNKNOWN → OVERDUE → RESULT_AVAILABLE. Уведомление не является сообщением пользователю вне этого окна.

Telegram, почта, системные toast, автозапуск Windows и автоматическое восстановление не настроены. WPF-окно запуска показывает общий operation state; подробное уведомление открывается в HTML-мониторе.

## Ограничения

Нужны работающий ноутбук и Watchdog. Обнаруживаются зарегистрированные операции; смысловой тупик reasoning без инструментального источника напрямую не определяется. Статус UI может быть DEGRADED, даже когда учёт операций достоверно работает. Живой PID и готовность плагина не доказывают продвижение. Независимый watchdog не является независимым исполнителем.
