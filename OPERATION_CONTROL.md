# Operation Control — общий контроль операций

Версия 1, 2026-10-16. Применяется к любой потенциально долгой операции: reasoning, plugin, browser, terminal, test, build, storage, other. n8n — один из возможных инструментов.

## Два разных механизма
Исполнитель регистрирует операцию и сохраняет доказательства результата. Отдельный процесс HQ Watchdog проверяет зарегистрированные операции текущего run, независимо от продолжающегося ChatGPT turn. Наблюдатель не запускает команды, не завершает процессы и не делает автоматический Retry.

Это кооперативная регистрация, не прозрачный перехват всех вызовов ChatGPT. Без регистрации coverage=NOT_REGISTERED; при регистрации — REGISTERED_OPERATIONS_ONLY. UI-наблюдение и общий таймер не гарантируют охват незарегистрированных действий.

## Перед вызовом
```
python scripts/task_lifecycle.py begin-operation --run <run-id> --kind plugin --tool <tool-name> --label "<short operation>" --expected-seconds 180 --check-every 10 --reference "<status/result reference>"
```
Сохранить возвращённый operation.id. Срок выбирать по конкретной операции, а не использовать один таймаут для всего. Интервал проверки 5–3600 секунд; срок 1–86400 секунд. Для долгой вычислительной части до её начала также нужна регистрация с ожидаемым сроком. Контроль ограничен работающим ноутбуком/процессом Watchdog.

Для side effect добавить `--side-effect --action-key <stable-business-action-key>`. Совпадающий ключ блокируется, пока в том же run есть RUNNING, WAITING_INPUT, FAILED или OUTCOME_UNKNOWN. Это защита на уровне run-record; она не обеспечивает идемпотентность внешней системы и не ловит действия вне регистрации/другого run. Перед восстановлением другого run также проверять его незавершённые действия.

Не записывать в метаданные секреты, полные ответы, токены, персональные тексты или URL с credentials. Использовать короткие ID, безопасные локальные пути и названия источников.

## После ответа и в ходе работы
```
python scripts/task_lifecycle.py operation-event --run <run-id> --operation <operation-id> --event observed --evidence-ref "<call-id/status-ref>" --note "Status source recorded"
```
Каждое событие требует `--evidence-ref` и короткую `--note`:

| Событие | Что доказано |
|---|---|
| observed | Источник проверен; progress/deadline не обновляются |
| progress | Есть содержательное продвижение; фиксируется last_progress_at |
| waiting-input | Нужен ответ пользователя; срок приостановлен до progress с доказательством ответа |
| extend | Подтверждён более долгий срок; требуется --expected-seconds от текущего времени; это не progress |
| succeeded | Результат проверен; PID/HTTP-доступность сами по себе этого не доказывают |
| failed | Ошибка подтверждена, требуется диагностика/решение |
| outcome-unknown | Фактический результат неизвестен; прямой переход в succeeded запрещён |
| resolve | После read-only диагностики установлен исход; --resolution SUCCEEDED / FAILED / NOT_EXECUTED |

Для реально запущенного локального процесса можно добавить `--pid <pid>` при регистрации или событии. Сохраняется PID + время создания; Watchdog проверяет эту пару с заданным интервалом. ALIVE доказывает только наличие того же процесса. Исчезновение, недоступность или переиспользование PID дают OUTCOME_UNKNOWN, включая нормальный exit без записанного результата. Исполнитель обязан проверить exit code/артефакты и записать succeeded/failed.

Для удалённых плагинов в этой версии нет универсального автоматического status API. Записывать call_id/execution_id/result reference в evidence-ref; при контрольном сроке исполнитель выполняет доступную read-only проверку соответствующим плагином. Если источника нет — исход остаётся неизвестным. Доступность плагина не равна выполнению его конкретного задания.

## Что показывает наблюдатель
| Operation state | Состояние задачи | Действие |
|---|---|---|
| WAITING_RESULT | WAITING_RESULT | Зарегистрированная операция ожидается в пределах срока; продвижение не утверждается |
| OVERDUE | CHECK_REQUIRED | Срок истёк; нужна read-only диагностика, сбой ещё не доказан |
| OUTCOME_UNKNOWN | UNKNOWN | Нельзя установить результат; без слепого повторения |
| FAILED | ERROR | Зафиксирована ошибка, проверить и исправить |
| WAITING_INPUT | WAITING | Явное ожидание ответа пользователя |

Ошибка UI или недоступность инструмента могут иметь приоритет над состоянием операции. Все операции доступны в `/api/status` → operation_watch; HTML показывает общий статус и первую незакрытую операцию. Состояния наблюдателя не переписывают run-record и не продлевают дедлайн.

## Завершение и восстановление
Активные, ожидающие ввода, failed, unknown и повреждённые операции блокируют finish и prepare-report. Для failed/unknown сначала записать диагностические доказательства и resolve. Resolve означает установленный исход, а не автоматически успешную задачу: исправление и новые обязательные verify/Quality Gate остаются необходимыми по задаче. После новых execute старые verify/Quality Gate сбрасываются.

Периодическое observed, запись updated_at и проверка PID не обновляют semantic last_progress_at или marker. Для старых run без last_progress_at временно используется updated_at; старые записи не переписываются при чтении. Проверка времени не доказывает смысловой тупик модели и не может сама возобновить остановившийся ChatGPT turn. Для такого восстановления нужен отдельный исполнитель/диспетчер, которого эта версия не добавляет.


## Адаптеры 1.3 — 2026-10-16
Текущая реализация описана в OPERATION_ADAPTERS.md. Явные локальные команды можно запускать через observed_process.py: exit evidence отделяется от semantic validation. RESULT_AVAILABLE требует проверки и operation-event succeeded; finish остаётся заблокированным до подтверждения. Для n8n поддерживается свежий metadata snapshot точного execution через существующий плагин ChatGPT и команду observe-n8n. Монитор сам к n8n не обращается; устаревший снимок даёт UNKNOWN. Обновление наблюдения не продлевает deadline/progress. HTML Attention / Next action и API notification — локальные уведомления, без внешней отправки. Старые описания отсутствия конкретных адаптеров относятся к версии 1.2; универсального status API для всех инструментов по-прежнему нет.
