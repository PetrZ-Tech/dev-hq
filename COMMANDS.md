# Dev HQ — Command Layer

Назначение: единый реестр коротких команд штаба. пользователь может писать их естественным языком; точное совпадение регистра и пунктуации не требуется.

## Общие правила
- Команды не отменяют `SECURITY_BOUNDARIES.md`, `STATE_FRESHNESS.md`, `SESSION_HANDOFF.md`, `MODEL_ROUTING.md`, `QUALITY_GATE.md`, `DECISION_MEMORY.md`, `CODEX_HANDOFF.md`, `RESOURCE_CONTROL.md` и `BACKUP_POLICY.md`.
- Имя/алиас проекта разрешать через `PROJECTS_REGISTRY.md`; не просить повторять уже зарегистрированный контекст.
- Если команда однозначна — выполнять сразу, без лишнего подтверждения.
- Если указанный проект неоднозначен — задать один короткий уточняющий вопрос.
- Read-only команды выполнять самостоятельно.
- Записи внутри `<PROJECTS_ROOT>\...` допустимы по правилам штаба; внешние/системные/необратимые действия требуют подтверждения.
- Для live-фактов применять `STATE_FRESHNESS.md`; не выдавать README/старый Source за текущее состояние.

## Команды

### 1. `Продолжаем <проект>`
Алиасы: `Вернёмся к <проект>`, `Открой <проект>`, `Продолжим <проект>`.
Режим: WORK.
Действие: разрешить проект → получить Codebase Memory → прочитать `PROJECT_STATE.md`/`PROJECT_CONTEXT.md` → при необходимости проверить live-систему → назвать текущий статус и ближайший Next → продолжить работу без повторного онбординга.

### 2. `Проверь штаб`
Алиасы: `Health check`, `Диагностика штаба`.
Режим: READ-ONLY.
Действие: использовать `HEALTH_CHECK.md`. `Проверь штаб полностью` — полный безопасный режим; `Глубокая диагностика штаба` — расширенный read-only тест.

### 3. `Покажи активные проекты`
Алиасы: `Что сейчас в работе?`, `Список активных проектов`.
Режим: READ-ONLY.
Действие: использовать `PROJECT_DASHBOARD.md` как основной агрегат, при необходимости обновить volatile Git/live-поля по `STATE_FRESHNESS.md`, затем показать активные проекты со статусом и ближайшим Next.

### 4. `Статус <проект>`
Алиасы: `Что с <проект>?`, `Где остановились на <проект>?`.
Режим: READ-ONLY.
Действие: показать VERIFIED LIVE/LOCAL, RECORDED, Open и Next по правилам свежести; если задача зависит от runtime, перепроверить специализированным инструментом.

### 5. `Что зависло?`
Алиасы: `Покажи блокеры`, `Где проблемы?`, `Что тормозит?`.
Режим: READ-ONLY.
Действие: по dashboard и свежим live/local данным собрать только реальные блокеры/ошибки/непроверенные критические участки. Не считать обычный backlog блокером. Если данных недостаточно — пометить `UNKNOWN`, не угадывать.

### 6. `Подготовь handoff`
Алиасы: `Зафиксируй состояние`, `Сохрани точку продолжения`.
Режим: CHECKPOINT.
Действие: для текущего/названного проекта выполнить `SESSION_HANDOFF.md`: проверить фактическое состояние → обновить `PROJECT_STATE.md` или `PROJECT_CONTEXT.md` → зафиксировать Checks/Open/Next → переиндексировать Codebase Memory. Не создавать handoff для одноразового вопроса без изменения состояния.

### 7. `Проверь проект перед коммитом`
Алиасы: `Pre-commit check`, `Готово к коммиту?`, `Quality Gate <проект>`.
Режим: QUALITY GATE.
Действие: следовать `QUALITY_GATE.md`: запустить `scripts/quality_gate.py` для проекта, проверить Git/diff/secrets и применимые test/typecheck/lint/build, затем отдельно проверить критерии текущей задачи. Итог только `PASS`, `WARN` или `FAIL`. Не делать commit/push. `--criteria-ok yes` ставить только после фактической проверки acceptance criteria.

### 8. `Сделай технический аудит <проект>`
Алиасы: `Аудит <проект>`, `Проверь архитектуру <проект>`.
Режим: READ-ONLY AUDIT.
Действие: Codebase Memory + локальные файлы + Git/GitHub + актуальная документация при необходимости. Проверить архитектуру, качество кода, тестирование, зависимости, ошибки/риски, состояние docs и deployment-контура. Сначала отчёт; исправления — только отдельной задачей.

### 9. `Покажи roadmap штаба`
Алиасы: `Что дальше по штабу?`, `План развития штаба`.
Режим: READ-ONLY META.
Действие: читать `HQ_ROADMAP.md`, показать DONE / IN PROGRESS / PARTIAL / PLANNED и ближайший активный пункт.

### 10. `Следующий шаг штаба`
Алиасы: `Что делаем дальше?` в контексте HQ.
Режим: META WORK.
Действие: взять первый `IN PROGRESS` из `HQ_ROADMAP.md`; если его нет — первый `PLANNED`, перевести в `IN PROGRESS` только когда реально начинаем выполнение.

### 11. `Обнови память <проект>`
Алиасы: `Переиндексируй <проект>`, `Обнови Codebase Memory <проект>`.
Режим: MAINTENANCE.
Действие: разрешить проект через реестр и переиндексировать его Codebase Memory; затем сообщить coverage/parse-проблемы, если есть.

### 12. `Покажи команды штаба`
Алиасы: `Что умеет штаб?`, `Команды HQ`.
Режим: READ-ONLY META.
Действие: вывести краткий список пользовательских команд из этого файла, без внутренних технических деталей.

### 13. `Создай новый проект <название>`
Алиасы: `Новый проект <название>`, `Заведи проект <название>`, `Bootstrap project <название>`.
Режим: BOOTSTRAP.
Действие: следовать `PROJECT_BOOTSTRAP.md`: проверить конфликт ID/alias/path → dry-run локального генератора → создать scaffold внутри `<PROJECTS_ROOT>` → проверить Git/files → индексировать Codebase Memory → зарегистрировать проект в `PROJECTS_REGISTRY.md` → обновить `PROJECT_DASHBOARD.md`. Не создавать remote repository, commit/push, dependencies или production без отдельного запроса.

### 14. `Запиши решение: <тема>`
Алиасы: `Создай ADR`, `Зафиксируй архитектурное решение`, `Запомни почему выбрали <тема>`.
Режим: ADR WRITE.
Действие: следовать `DECISION_MEMORY.md`: разрешить проект → проверить существующие ADR → собрать Context / Decision / Why / Alternatives / Consequences → создать новый `ADR-XXXX` → обновить ADR index → переиндексировать Codebase Memory. Не создавать ADR для тривиальных implementation details.

### 15. `Почему мы решили <тема>?`
Алиасы: `Почему выбрали <тема>?`, `Покажи решение по <тема>`.
Режим: ADR READ.
Действие: найти релевантный ADR через Codebase Memory и локальный `docs/adr`; вернуть кратко Decision + Why + Consequences + статус ADR. Не отвечать догадкой, если ADR не найден.

### 16. `Покажи решения <проект>`
Алиасы: `ADR <проект>`, `Архитектурные решения <проект>`.
Режим: ADR READ.
Действие: прочитать `docs/adr/README.md` и/или Codebase Memory, показать принятые/заменённые решения без пересказа всего содержимого.

### 17. `Подготовь handoff для Codex <проект>: <задача>`
Алиасы: `Подготовь промпт для Codex`, `Собери задачу для Codex`, `Codex handoff <проект>`.
Режим: CODEX HANDOFF.
Действие: следовать `CODEX_HANDOFF.md`: разрешить проект → поднять свежий state/Codebase Memory → определить минимальный relevant-file set → выбрать complexity/model/effort по `MODEL_ROUTING.md` → сформировать acceptance/verification/guardrails → создать handoff через `scripts/build_codex_handoff.py`. Всегда сообщать рекомендуемые model + reasoning/effort.

### 18. `Передай в Codex`
Алиасы: `Запусти это в Codex`, `Отдай Codex`.
Режим: CODEX TRANSFER.
Действие: использовать уже подготовленный handoff. Если текущий runtime реально предоставляет active Codex `turn_token`, допускается Native2 transfer. Если token/active turn отсутствует — статус `⏸ CONTEXTUAL`; показать готовый handoff и не утверждать, что Codex запущен. Не использовать browser automation как скрытую замену Native2 без отдельного решения.

### 19. `Покажи расход ресурсов`
Алиасы: `Покажи расход лимитов`, `Resource usage`, `Что по лимитам?`.
Режим: RESOURCE REPORT.
Действие: следовать `RESOURCE_CONTROL.md`: прочитать локальный ledger через `scripts/resource_tracker.py report`; если текущий интерфейс безопасно даёт read-only Usage/Allowance, дополнительно получить фактические platform данные. Всегда разделять `LOCAL LEDGER` и `PLATFORM USAGE`; если platform usage недоступен — не оценивать и не выдумывать остаток.

### 20. `Сделай backup <проект>`
Алиасы: `Backup <проект>`, `Сделай checkpoint <проект>`, `Резервная копия <проект>`.
Режим: BACKUP WRITE.
Действие: следовать `BACKUP_POLICY.md`: разрешить проект через registry → выполнить dry-run при новой/необычной конфигурации → создать backup через `scripts/backup_project.py create` → автоматически проверить ZIP/manifest/hashes. Backup хранится только внутри `<PROJECTS_ROOT>\_hq_backups`. Не архивировать secrets/.env/private keys/local DB по умолчанию; не удалять старые backup автоматически.

### 21. `Проверь backup <проект>`
Алиасы: `Проверь резервную копию <проект>`, `Verify backup <проект>`.
Режим: BACKUP READ/VERIFY.
Действие: проверить последний архив через `scripts/backup_project.py verify`, включая ZIP integrity, manifest и SHA-256 каждого сохранённого файла.

### 22. `Покажи backup <проект>`
Алиасы: `Список backup <проект>`, `Какие есть резервные копии <проект>`.
Режим: BACKUP READ.
Действие: показать последние архивы через `scripts/backup_project.py list`; не удалять и не восстанавливать автоматически.

### 23. `Покажи окна`
Алиасы: `Какие окна открыты?`, `Windows GUI status`.
Режим: DESKTOP READ.
Действие: через Desktop Control Adapter выполнить read-only `windows`; показать только значимые видимые окна. Если desktop locked/offline — сообщить об этом, не переходить к raw input.

### 24. `Покажи элементы <окно>`
Алиасы: `Что есть в окне <окно>?`, `UI controls <окно>`.
Режим: DESKTOP READ.
Действие: через Desktop Control Adapter выполнить `controls`; предпочитать Name/AutomationId и semantic patterns. Не использовать screenshot, если UIA уже даёт нужную информацию.

### 25. `Работай в приложении <окно>: <задача>`
Алиасы: `Сделай в программе <окно> ...`, `Управляй <окно>`.
Режим: DESKTOP WORK.
Действие: следовать skill `desktop-control-adapter`: UIA controls first → screenshot при необходимости → keyboard/mouse только fallback. GUI writes подчиняются `SECURITY_BOUNDARIES.md`; password/2FA вводит пользователь вручную; protected/system target требует отдельного подтверждения; после действия обязательно проверить результат.

### 26. `Выполни задачу под ключ <проект>: <задача>`
Алиасы: `Сделай под ключ`, `Доведи задачу до результата`, `Полный цикл <проект>`.
Режим: FULL LIFECYCLE.
Действие: TASK_LIFECYCLE.md + STAGED_EXECUTION.md: resolve project → согласовать архитектуру/ТЗ и этапы → выполнять согласованный план подэтапами → verify/checkpoint → продолжать при отсутствии блокера. До потенциально долгих операций — OPERATION_CONTROL.md. Run-record может быть единым. Не завершать при PENDING/FAIL или незакрытых операциях. Confirmation gates сохраняются.

## Разбор естественного языка
Команда не обязана быть написана дословно. Если намерение очевидно, сопоставить его с ближайшей командой. Например, `продолжаем проект X` = поднять его актуальный state; `почему приняли это решение?` = прочитать соответствующий ADR; `подготовь handoff для внешнего coding tool` = собрать минимальный проверяемый пакет контекста.

Если сообщение содержит и команду, и конкретную задачу — сначала поднять актуальный контекст проекта, затем сразу перейти к задаче.

## Формат ответа
- Не повторять длинный внутренний процесс.
- Для статуса: `Сейчас` → `Проверено` → `Next`.
- Для Quality Gate: первая строка `Quality Gate: PASS|WARN|FAIL`, затем только Git / tests-build / secrets / task criteria / реальные проблемы.
- Для ADR lookup: `Решение` → `Почему` → `Последствия` → ссылка/номер ADR.
- Для аудита/проверки: сначала итог, затем только значимые проблемы.
- Для выполненной рабочей команды: что изменено + чем проверено + следующий шаг.
